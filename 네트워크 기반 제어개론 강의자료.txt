## [L01 / PDF 008 / L1-8] Benefits and Drawbacks of DDC
@@TEXT_BEGIN
Benefits and Drawbacks of DDC

◼ Benefits
   ● Easy configuration, reconfiguration, parameterization of control
     loops
   ● Easy self-tuning of control parameters
   ● Possibility of realization of advanced control algorithms
   ● Comprehensive data acquisition and presentation


◼ Drawbacks (in the past)
   ● Low fail-safety of the system
   ● Higher investment, maintenance, personnel costs (eg. programming)
   ● Overloads of CPU and difficulties in programming
@@TEXT_END

@@TEXT_BEGIN
Centralized Architecture - Advantages

◼ 1960s - 1980s
◼ Devices with analog wiring back to computer
◼ Powerful CPU for control, monitoring, interface etc

   ● “Put all your eggs in the one basket and watch that basket”
   ● Better operating environment for digital electronics
       ❖ Put machine in sheltered area away from combustion,
         environment
   ● Simpler software model
       ❖ All changes are made in one place in the system

Centralized Architecture - Disadvantages

## [L01 / PDF 030 / L1-30] Networked Architecture Advantages (4/6)
@@TEXT_BEGIN
Networked Architecture Advantages (4/6)

◼ Self-diagnosis and predictive maintenance
   ● Local diagnosis with internal sensors provide extra information on
     the device condition (eg. motor currents)
   ● Process information logged via a network
   ● Performance data collected and analysed off-line
   ● Can anticipate faults while the equipment is operating -> Reduction
     in system shutdown for maintenance work
   ● Can replace faulty subcomponents before serious system failure
   ● Easier on-line repair (“hot swap”)
@@TEXT_END

## [L01 / PDF 031 / L1-31] Networked Architecture Advantages (5/6)
@@TEXT_BEGIN
Networked Architecture Advantages (5/6)

◼ “Abnormal situations” costs $20billion/year in US
◼ Improved reliability
   ● Reliability is the most critical requirement (e.g. 80% of
     unexpected plant shutdown was caused by actuators)
   ● Less ext connection, complexity, interference, noise, etc
   ● Improved robustness against dust & vibration
◼ Improved fault-tolerance based on redundancy
   ● Different nodes can cross-check each other
   ● Error detection within a node
   ● Graceful degradation
◼ Enhanced safety & environment protection
   ● Reliable shutdown system - smart actuators can remain in
     operation despite system failures
   ● Early detection of valve leaks
@@TEXT_END

## [L02 / PDF 006 / L2-6] Networked Architecture Challenges (2)
@@TEXT_BEGIN
Networked Architecture Challenges (2)

◼ New difficulties in the system safety issues
◼ Processing site failures: Processors are independent of each
  other
   ● A processor failure implies that the remaining sites need to “detect
     and handle” that failure in some way
   ● (Eg) Redistribution or switching to other modes
◼ Transmission delays
   ● Not necessarily failures, but can certainly lead to failures: A delay
     can be misconstrued as a lost message!
   ● Variable delays (jitter) due to different route, high bus traffic,
     processing delay, intermittent failures, etc.
   ● Also leads to the data inconsistency problem: Different nodes see
     the same set of messages in a different order

## [L02 / PDF 013 / L2-13] Network Speed & Bandwidth
@@TEXT_BEGIN
Network Speed & Bandwidth

◼ Bandwidth (=data rate)
   ● The number of bits that can be transmitted per second
   ● (eg) CAN 1 Mb/s, Ethernet 1Gb/s

◼ Bus speed = 1/bandwidth = bit time (Tbit)
   ● The time to transmit 1 bit of data over the network
   ● (eg) Tbit=1us for 1 Mb/s CAN, 1ns for 1 Gb/s Ethernet

◼ Bandwidth is constrained by:
   ● The cabling method (eg. twisted pairs, co-axial)
   ● Line length
   ● Immunity to interference
@@TEXT_END

## [L02 / PDF 017 / L2-17] Network Delay - Processing & Queuing Time
@@TEXT_BEGIN
Network Delay - Processing & Queuing Time


◼ Pre-processing (Tpre) and post-processing time (Tpost)
   ● Encoding the data into a packet (at the sender)
   ● Decoding the packet into a physical data (at the receiver)
   ● Depend on the device (software & hardware)


◼ Queuing delay or waiting time (Twait)
   ● The time taken by a packet to gain access to the buffer of a
     network controller and to win an arbitration after being queued
   ● Depends on:
      ❖ Media Access Control (MAC) mechanism
      ❖ Network traffic load
      ❖ Number of nodes
      ❖ Relative priority (nodes, messages)
@@TEXT_END
@@PAGE_END lecture=L02 pdf_page=017

## [L02 / PDF 018 / L2-18] Network Delay - Transmission Time
@@TEXT_BEGIN
Network Delay - Transmission Time


◼ Transmission time (Ttx)
   ● The time taken for the packet to physically travel along the bus
     channel once it has gained the access to the bus
   ● Determined by data rate, message size, distance between two
     nodes:
                      Ttx = Tframe + Tprop
      Tframe = the time required to send the packet = nbit x Tbit
      Tprop = propagation time between two nodes
@@TEXT_END

@@PAGE_BEGIN lecture=L02 pdf_page=019 slide_label="L2-19" slide_title="Network Delay - Frame Time & Propagation Time" image_xobjects=0
## [L02 / PDF 019 / L2-19] Network Delay - Frame Time & Propagation Time
@@TEXT_BEGIN
Network Delay - Frame Time & Propagation Time

◼ Propagation time (Tprop)
   ● The time interval for one bit to travel from one end of the channel
     to the other end
   ● Assumed to be 2/3 of the speed of light, typically 5s/km

◼ Frame time (Tframe)
   ● Depends on the size of data, overhead, any padding/stuffing bits,
     and bit time
    Tframe = [Ndata + Noverhead + Npad + Nstuff] x 8 x Tbit
               where, N is number of bytes

◼ (eg) To send 1 bit of data
   ● 6-byte over CAN @500kbps -> Tframe= 6x8x2us = 96us
   ● 84-byte over Ethernet @10Mbps -> Tframe=84x8x0.1us =67us
@@TEXT_END

## [L02 / PDF 020 / L2-20] Jitter
@@TEXT_BEGIN
Jitter


◼ Jitter - the variability in the delay
◼ Cause of jitter
   ● Message collision
   ● Scheduling
   ● Branching in the code
   ● Clock drift
◼ Effects on control systems - signal distorted and making the
  system time-varying
   ● Performance degradation and instability
   ● Compensation of jitter results in extra costs and the change in
     control method (eg. stochastic method, time-varying approach)

   ● Errors must be detected

   ● Packet dropouts must be detected by a receiver
   ● The protocol is responsible for detecting errors in nodes

@@TEXT_BEGIN
DLL - MAC - Uncontrolled


◼ No external control signal (either token or time)
◼ The arbitration is based on bus status and hardware logic in the

◼ Known as Carrier Sense Multiple Access (CSMA) -> A node

  -> Collisions may occur which need to be resolved
◼ Flexibility - the protocol does not need changing if nodes are
  added or removed
◼ Typical forms of uncontrolled protocols:
   ● CSMA with collision detection (CSMA/CD)
   ● CSMA with collision avoidance (CSMA/CA)
   ● Non-destructive bitwise arbitration

## [L03 / PDF 037 / L3-37] DLL - MAC - Uncontrolled - CSMA/CD
@@TEXT_BEGIN
DLL - MAC - Uncontrolled - CSMA/CD


◼ Operation
  ● A node waits for the bus to become idle before it transmits
  ● If two nodes transmit simultaneously, a collision occurs and each
    node waits for a random time before re-trying
◼ Characteristics
  ● The protocol supports a large number of nodes
  ● Nodes can enter and leave the network without requiring any
    initialisation or reconfiguration of the network
  ● Efficient for aperiodic messages and low traffic -> collisions very
    rarely occur
  ● Under heavy load -> collisions occur frequently, leading to re-tries
    -> poor determinacy (unbounded latency) and low efficiency
  ● The detection of a collision requires hardware logic in the node
◼ Example
  ● Ethernet (IEEE 802.3)
@@TEXT_END

DLL - MAC - Uncontrolled - CSMA/CA

◼ Similar to CSMA/CD in the sense that each node
  waits for the bus to become quiet before
  transmitting, but each node uses a timer to ensure

◼ Each node has a unique timer value which effectively
  provides a slot assignment
◼ (Eg) Zigbee, ARINC-629, LON

@@TEXT_BEGIN
DLL - MAC - Uncontrolled - Bitwise (1)

◼ Non-destructive bitwise
   ● The message identification provides the basis of arbitration
   ● Nodes with the highest priority gain immediate access to the bus
     and continue transmitting their message whereas, nodes with a
     lower priority stop and contend for bus access later
   ● The priority arbitration is based on a “wired-AND” logical function -
     the message with the lowest binary number for an identifier wins
     the arbitration
◼ Also called:
   ● CSMA/Priority Collision
     Resolution, CSMA/AMP,
     CSMA/CA, Binary count
     down, Variant CSMA/CD
◼ Example
   ● CAN

@@TEXT_BEGIN
DLL - MAC - Uncontrolled - Bitwise (2)


◼ Advantages
  ● The prioritisation is based on message identifiers rather than
    node identifiers
  ● Low latency is guaranteed for high priority nodes
  ● The network still functions in overload conditions
  ● The protocol is efficient - arbitration is incorporated in the
    message transmission
◼ Problems
  ● Propagation delay limits bus length
  ● Access to the bus cannot be guaranteed for low priority
    messages under heavy loads

## [L03 / PDF 042 / L3-42] DLL - Flow Control
[VISUAL_ASSETS] This page contains 1 image object(s); selectable PDF text is extracted below.
@@TEXT_BEGIN
DLL - Flow Control

◼ Flow control - a protocol to control the speed of information
  flow between a sender and a receiver nodes
◼ Since a receiver must keep up with a sender -> the receiver
  determines the maximum speed of communication
◼ Implemented at the Data Link Layer on top of the MAC protocol
◼ Two types of flow control
   ● Explicit flow control
   ● Implicit flow control
@@TEXT_END
@@PAGE_END lecture=L03 pdf_page=042

@@PAGE_BEGIN lecture=L03 pdf_page=043 slide_label="L3-43" slide_title="DLL - Flow Control - Explicit Method" image_xobjects=0
## [L03 / PDF 043 / L3-43] DLL - Flow Control - Explicit Method
@@TEXT_BEGIN
DLL - Flow Control - Explicit Method

◼ The receiver sends an explicit acknowledgement message
  to inform the sender that the message was received (and
  that the receiver is ready for another message)
  -> The receiver controls the throughput between two
  nodes
◼ The receiver must detect and discard duplicate messages
  and send acknowledgements to each received message
◼ Note that:
   ● The sender initiates the communication
   ● The receiver can delay the sender
   ● A communication error is detected by the sender - NOT the
     receiver
   ● Time redundancy is used - potentially increasing the protocol
     latency (and jitter)
@@TEXT_END
@@PAGE_END lecture=L03 pdf_page=043

## [L03 / PDF 044 / L3-44] DLL - Flow Control - Explicit Method : PAR
[VISUAL_ASSETS] This page contains 1 image object(s); selectable PDF text is extracted below.
@@TEXT_BEGIN
DLL - Flow Control - Explicit Method : PAR

◼ The PAR (Positive Acknowledgement or Retransmission)
  protocol is widely used in event-triggered communication
   1. When the sender has a message to send, it resets a timeout
      counter
   2. If the sender receives an acknowledgement, the transmission is
      successful
   3. If an acknowledge does not arrive within the timeout interval, the
      sender resets the timeout counter and repeats steps 1-3
   4. If step 3 fails after
      a maximum
      number of retries,
      the transmission is
      abandoned


             Distribution of latency of PAR
@@TEXT_END
@@PAGE_END lecture=L03 pdf_page=044

@@PAGE_BEGIN lecture=L03 pdf_page=045 slide_label="L3-45" slide_title="DLL - Flow Control - Implicit Method (1)" image_xobjects=0
## [L03 / PDF 045 / L3-45] DLL - Flow Control - Implicit Method (1)
@@TEXT_BEGIN
DLL - Flow Control - Implicit Method (1)


◼ The sender and receiver agree (before system start-
  up) on the times when messages are sent
◼ Messages are only sent at the agreed points in time
  and the receiver agrees to accept all messages sent
  by the sender
◼ There are no acknowledgements
◼ Error detection is the responsibility of the receiver
   ● A message may contain an error
   ● A message may not arrive at the anticipated time
◼ Both the sender and receiver use identical versions
  of time -> a need for synchronisation of all nodes
@@TEXT_END
@@PAGE_END lecture=L03 pdf_page=045

## [L03 / PDF 046 / L3-46] DLL - Flow Control - Implicit Method (2)
@@TEXT_BEGIN
DLL - Flow Control - Implicit Method (2)


◼ Some degree of fault tolerance is possible by sending
  k copies of a message
   ● The communication is complete if one correct message is
     received
◼ Implicit flow control is well-suited to multicast
  communication
◼ Note that:
   ● Transmission is uni-directional
   ● The sequence of message is determined by the designer and
     is not changed when the system is running
@@TEXT_END

## [L03 / PDF 047 / L3-47] DLL - Flow Control - Thrashing
@@TEXT_BEGIN
DLL - Flow Control - Thrashing


◼ A phenomenon which occurs when the throughput
  decreases suddenly with increasing load of the bus
◼ Main causes
   ● Extra load generated by the retry mechanism in event-
     triggered networks
   ● Task switching by an operating system -> reduces the
     amount of time available to send messages or introduces
     latencies
◼ To avoid thrashing in explicit flow control
   ● To monitor the bus loading and to modify the flow control to
     reduce the bus traffic (e.g. removing low priority transfers
     for a short time)
@@TEXT_END

Summary - Common Technology of Fieldbus

   ●   Guaranteed delivery within a deadline (worst-case conditions)
   ●   Low latency with minimal variation (jitter)
   ●   Autonomous and validated independently of applications
   ●   Flexibility to accommodate changes
   ●   Fault tolerance

◼ Physical layer: encoding types, drivers
◼ Flow control
   ●   Explicit: PAR for event-triggered -> thrashing
   ●   Implicit: TDMA for time-triggered
◼ MAC protocols
   ●   Controlled explicitly (time-multiplexed): master-slave(poll), token
   ●   Controlled implicitly: time-triggered(TDMA)
   ●   Uncontrolled (random access with retransmission): CSMA/CD, CSMA/CA
   ●   Uncontrolled (random access with prioritization): Bitwise arbitration

[VISUAL_ASSETS] This page contains 1 image object(s); selectable PDF text is extracted below.
@@TEXT_BEGIN
CAN Overview

◼ Controller Area Network (CAN) introduced by Bosch in 1986
   ●   To support short messages (up to 8 bytes)
   ●   Multi-master access (collisions are resolved)
   ●   A high degree of reliability (15-bit CRC)
   ●   Multicast simultaneously to all nodes
◼ ISO-11898 supports the PHY and DLL
   ● PHY - signalling, encoding, bit timing, bit synchronisation
   ● DLL - bus arbitration, message framing, message validation, error
     detection, fault confinement
◼ Application Layer for higher layer protocols (CAL, CANopen, etc)
◼ Wide user group including the automotive industry
@@TEXT_END

   ● Clock drift makes receivers lose track of bits
   ● Periodic edges allow receiver to resynchronize to sender clock

   ● If 5 consecutive 0s or 1s are detected, a 6th bit of opposite polarity

DLL - Data Frame - Identifier Field

   ● Known as ‘content addressing’ or ‘source addressing’

## [L04 / PDF 020 / L4-20] DLL - Data Frame - Identifier Field - Arbitration (1)
@@TEXT_BEGIN
DLL - Data Frame - Identifier Field - Arbitration (1)

◼ Carrier Sense Multiple Access (CSMA) with bus arbitration to
  resolve collisions - Arbitration occurs as these bits are
  transmitted
   ● If no collision -> transmitted directly
   ● If collision occurs -> messages are ANDed bit-wise
◼ The node with the lowest binary number wins the arbitration
  and continues transmitting without delay or interference from
  other nodes (non destructive arbitration)
◼ Advantages
   ● Guaranteed low latency for high priority messages
   ● No re-tries in overload situations
@@TEXT_END

## [L04 / PDF 025 / L4-25] DLL - Error Handling (1)
@@TEXT_BEGIN
DLL - Error Handling (1)

◼ CAN detects the following errors:
  ● Bit errors - transmitted bits are monitored as they
    are placed on the bus (detected by the sending
    node)
  ● Bit stuffing errors - 6 identical bits
  ● CRC - a 15 bit CRC is calculated by the
    transmitter and the receiver, and checked at the
    receiver
  ● Form bits - the number of bits transmitted
    corresponds to the size
  ● Acknowledgement errors - no acknowledge bit set
@@TEXT_END
@@PAGE_END lecture=L04 pdf_page=025

@@PAGE_BEGIN lecture=L04 pdf_page=026 slide_label="L4-26" slide_title="DLL - Error Handling (2)" image_xobjects=0
## [L04 / PDF 026 / L4-26] DLL - Error Handling (2)
@@TEXT_BEGIN
DLL - Error Handling (2)

◼ If an error is detected by any of the other nodes, the
  current transmission is stopped by transmission of
  an active error frame by at least one node (receiver)
   ● Active error frame (6bit “0”) -> bit stuff error
   ● Passive error frame (6bit “1”) -> can be overrun by active error
     frame
◼ An active error frame contain six consecutive 0s ->
  to violate bit stuffing rule which will be detected by
  other nodes
◼ If transmitter sees that it has been pre-empted by
  an error frame, it attempts retransmission after 23-
  bit time
@@TEXT_END

   ● A message is only transmitted when an event occurs
   ● Flexible allocation of bus bandwidth
◼ Not suitable for hard real-time applications due to
  the use of uncontrolled MAC
   ● Not predictable - Events happen randomly
   ● Not deterministic - Random access and retransmissions lead
     to randomly varying latency
   ● Not robust - Multiple nodes may result in a collision, and
     potential loss or corruption of data
   ● Efficiency is low under high bus loadings - a higher bus rate
     required
   ● Hard to implement a fault-tolerant mechanism (eg. Fault
     detection, redundant channel, bus guardian, etc.)
   ● Analysis in the presence of random delays is very difficult
@@TEXT_END

## [L05 / PDF 006 / L5-6] System Fail Due To Communication Failure
@@TEXT_BEGIN
System Fail Due To Communication Failure

◼ Even with properly working network hardware,
  messages can be lost due to collisions or corruption
  by noise
◼ Even if message losses are relatively infrequent, long
  periods of operation multiplied by many units in the
  field can cause the safety problem
  ● -> Therefore, the system must be built so as not to fail
    unless three or more messages are lost in a row


  P.Koopman, “Lost messages and system failures,” Embedded Systems Programming, 9(11), pp.38-
  52, Oct 1996.

## [L05 / PDF 007 / L5-7] Bit Errors Due To Noise
@@TEXT_BEGIN
Bit Errors Due To Noise

◼ Any time a message is transmitted, there is a non-
  zero probability that some of the bit in the message
  will be corrupted by noise
◼ Message error rate
  = 1 - (1 - bit_error_rate)bits per message
◼ (eg) bit error rate = 10-9, a typical message is 96
  bits long
   ● The message error rate is 1 - (1-10-9)96 = 0.0000000096, or
     0.00000096% of messages will be lost due to bit errors
   ● For a system running at 100 messages/s, approximately 30
     system failures/year can be expected because of noise
@@TEXT_END

## [L05 / PDF 009 / L5-9] Time Triggered Protocols
@@TEXT_BEGIN
Time Triggered Protocols

◼ Time-triggered networks are capable for safety-critical
  systems
◼ Predictable
   ● Exact time point of a certain message is known
   ● Messages are triggered on the basis of the progression of time
     (global time reference)
◼ Deterministic
   ● Each node (message) gets a time slot in the transmission loop
     where only it can send a message -> No collision, no arbitration
◼ Efficient and low overhead
   ● No arbitration required
   ● Efficient under high bus loads -> higher bus rate achievable
◼ Easy to implement fault-tolerance mechanisms
   ● Voting, redundancy, bus guardian, etc
◼ (eg) TTCAN, Flexray, TTP/C, EtherCAT, TTEthernet
@@TEXT_END

## [L05 / PDF 011 / L5-11] Benefits of Time-Triggered System
@@TEXT_BEGIN
Benefits of Time-Triggered System

## [L06 / PDF 019 / L6-19] Internal vs External (1)
@@TEXT_BEGIN
Internal vs External (1)

◼ Internal synchronization
   ● Clocks are to be synchronized only with respect to each
     other -> To establish an approximate global time
   ● Internally synchronized clocks drift from the external time if
     the clocks are never resynchronized with the external time
     base
◼ External synchronization
   ● To minimise the discrepancy between an external time
     reference (eg., GPS) and the approximate global time
   ● If all clocks are externally synchronized, then the clocks are
     also internally synchronized
◼ Approximate global time reference (internal
  synchronization) is more critical than external
  reference (external)
@@TEXT_END

◼ Distributed structure
  ● Each node plays the same role and executes the whole clock

## [L06 / PDF 025 / L6-25] Deterministic vs Probabilistic
@@TEXT_BEGIN
Deterministic vs Probabilistic

◼ Deterministic algorithms
   ● An upper bound on the clock skew is guaranteed
   ● The best precision is limited by the number of clocks and
     message delays (with distributed structure)
◼ Probabilistic algorithms
   ● Stochastic nature of message delay is modelled as a
     synchronization parameter
   ● Achieve better precision
   ● The requesting node sends a “request” message repeatedly
     to read the target node’s clock until the required minimum
     response time D is achieved
   ● The network load increases as the desired skew reduces
   ● If the maximum number of attempts to read the remote
     clock values is limited, the desired response time D may not
     be achieved -> Probability of synchronization failure
@@TEXT_END

## [L06 / PDF 027 / L6-27] Resynchronization Detection Block
@@TEXT_BEGIN
Resynchronization Detection Block

◼ To trigger each node to start the clock synchronization
  algorithm
◼ Round-based algorithms—The synchronization algorithm is
  periodically initialised
   ● Assumed that all the clocks are initially synchronized
   ● Each clock starts the k-resync round when its logical clock reaches
     time kR (R=Resync interval)
◼ Message exchange method
   ● Each clock sends a message when its logical clock reaches the
     multiple of R
   ● A resynchronization round starts when it receives a predetermined
     number of clock values
◼ For time-triggered systems
   ● Assumed that delivery time for each message is known
   ● Each node runs resynchronization continuously when any message
     is delivered (i.e., comparing the deviation between the expected
     and the actual arrival time)
@@TEXT_END

◼ Remote clock reading (RTR) technique

## [L06 / PDF 030 / L6-30] Clock Correction Block - Logical Clock Correction (1)
@@TEXT_BEGIN
Clock Correction Block - Logical Clock Correction (1)

◼ State correction (offset correction)
   ● The adjustment term is added to the offset
   ● Easy to implement
   ● Lower precision if there is a large difference
     between drift rates of the clocks
   ● Abrupt change of the logical clock (eg., clocks can
     set backward and the same nominal time value is
     reached twice)

## [L06 / PDF 031 / L6-31] Clock Correction Block - Logical Clock Correction (2)
@@TEXT_BEGIN
Clock Correction Block - Logical Clock Correction (2)

◼ Rate correction
   ● Changing the clock rate
   ● High precision and smooth running of the clocks
   ● Possibility of a global drift of the whole clock
     ensemble
◼ Hybrid correction
   ● Combination of state and rate corrections
   ● If the adjustment term is small, state correction is
     used
   ● If the adjustment term is large, rate correction is
     used

## [L06 / PDF 032 / L6-32] Clock Correction Block - Correction Term (1)
@@TEXT_BEGIN
Clock Correction Block - Correction Term (1)

◼ Convergence-averaging algorithms
   ● Apply an averaging algorithm to the collected
     clock values to estimate the approximate global
     time
   ● Interactive Convergence Function (CNV) (Lamport
     & Melliar-Smith, 1985)
       ❖Egocentric mean (skews bigger than D replaced
        with zero)
   ● Fault-Tolerant Average Function (FTA) (Kopetz,
     1987)
       ❖Average after removing f fastest and f slowest
        clocks (sorting required)
@@TEXT_END
@@PAGE_END lecture=L06 pdf_page=032

@@PAGE_BEGIN lecture=L06 pdf_page=033 slide_label="L6-33" slide_title="Clock Correction Block - Correction Term (2)" image_xobjects=0
## [L06 / PDF 033 / L6-33] Clock Correction Block - Correction Term (2)
@@TEXT_BEGIN
Clock Correction Block - Correction Term (2)

◼ Convergence-averaging algorithms (Cont’d)
  ● Fault-Tolerant Midpoint Function (FTM) (Lundelius
    & Lynch, 1988)
     ❖Uses max & min values after removing f
      slowest & f fastest clocks
  ● Fast Convergence Function (Gusella & Zatti, 1989)
     ❖Average of n-clock that are within D of at least
      m=(N-f) other clocks
◼ Convergence-non-averaging algorithms
  ● Use predefined value (i.e., expected arrival time)
    when a certain number (e.g, 2f+1) of messages
    are received
@@TEXT_END

## [L07 / PDF 011 / L7-11] A Software System Example
@@TEXT_BEGIN
A Software System Example

◼ Consider a software system:
   ● An incorrectly written statement in a program may decrement an
     internal variable instead of incrementing it (x++ -> x--)
   ● It will result in the incorrect value being written
   ● If other program statements then use this value, the whole system
     will deviate from its desired behaviour (u = Kp * x)
◼ In this example:
   ● Fault - the erroneous statement
   ● Error - an invalid value
   ● Failure - the behaviour resulting from the error
◼ Note:
   ● If the invalid statement is never executed, the fault will not lead to
     an error
   ● If the variable is never read after being written, no failure will occur
   ● The mere presence of errors or faults does not necessarily imply
     system failure
@@TEXT_END

@@TEXT_BEGIN
Fault Tree Analysis (FTA)

   ● DFTA (Dynamic FTA) with failure probability

## [L07 / PDF 034 / L7-34] Fault Tolerance
@@TEXT_BEGIN
Fault Tolerance

◼ The ability of a system to perform its function
  correctly (or at least a degraded version of it) even
  in the presence of internal faults
◼ To cope with run time faults in the operational phase
◼ The basis of all fault tolerant techniques is some
  form of redundancy
  ● If a component fails, one or more of the non-failed replicas
    continue to provide a service with no significant disruption
  ● Different types of redundancy available

## [L07 / PDF 035 / L7-35] Fault Tolerance - Types of Redundancy
@@TEXT_BEGIN
Fault Tolerance - Types of Redundancy

◼ Hardware redundancy
  ● Multiple replicas of a component for the same function
  ● The outputs are compared and any discrepancy is an
    indication of a fault in one or more components
  ● (eg) Triple Modular Redundancy (TMR)—The output of three
    independent components is compared and the output of the
    majority of the components is actually passed on
◼ Time redundancy (SW)
  ● Multiple independently developed versions of the same
    component
  ● (eg) The same software is executed on the same hardware
    during two different time intervals
◼ Analytical redundancy (SW)
  ● Information redundancy
  ● Based on mathematical models and control techniques
@@TEXT_END

Hardware Redundancy - Triplex

  locate the second failure

## [L07 / PDF 050 / L7-50] Fault Treatment - Standby Scheme (1/3)
@@TEXT_BEGIN
Fault Treatment - Standby Scheme (1/3)

◼ For permanent faults, the failed component must be
  replaced by a non-failed one -> some kind of
  ‘standby’ components required
  ● The standby component has to be integrated into the
    system
  ● Its state has to be synchronised with the state of the rest of
    the system
◼ Three general types of standby schemes
  ● Cold Standby
  ● Warm Standby
  ● Hot Standby
@@TEXT_END
@@PAGE_END lecture=L07 pdf_page=050

@@PAGE_BEGIN lecture=L07 pdf_page=051 slide_label="L7-51" slide_title="Fault Treatment - Standby Scheme (2/3)" image_xobjects=0
## [L07 / PDF 051 / L7-51] Fault Treatment - Standby Scheme (2/3)
@@TEXT_BEGIN
Fault Treatment - Standby Scheme (2/3)

◼ Cold Standby
  ● The standby component is not operational - no overhead
    during the normal operation
  ● Its state needs to be changed fully when the fault occurs ->
    large fault recovery time
  ● Expensive (inefficient)
◼ Warm Standby
  ● The standby component is used to keep the last checkpoint
    of the operational component that it is backing up
  ● When the principal component fails, the backward error
    recovery can be short
  ● Synchronisation is performed during checkpoints - high
    overhead
@@TEXT_END
@@PAGE_END lecture=L07 pdf_page=051

@@PAGE_BEGIN lecture=L07 pdf_page=052 slide_label="L7-52" slide_title="Fault Treatment - Standby Scheme (3/3)" image_xobjects=0
## [L07 / PDF 052 / L7-52] Fault Treatment - Standby Scheme (3/3)
@@TEXT_BEGIN
Fault Treatment - Standby Scheme (3/3)

◼ Hot Standby
  ● The standby component is fully active and duplicating the
    function of the primary component
  ● Recovery can be practically instantaneous
  ● Difficult to keep two components synchronised
     ❖Synchronisation has to be done on a constant basis
     ❖This requires communications between the primary and
      the standby - higher overhead than for warm standby
@@TEXT_END

  (important) failure

    behaviour

◼ A testing process includes:

     ❖ To execute the system based on the fault hypothesis
  ● Monitoring
     ❖ To collect information (state, outputs) for debugging
  ● Debugging
     ❖ To find the errors that cause the failure (through replay)

Testing - Testability

◼ The probability for failures to be observed during testing
  when errors are present - “Is the system easy to test?”

   ●   Cost reduction - testing can be more than half of the development

## [L08 / PDF 012 / L8-12] Testing - Monitoring - Basic Concepts
@@TEXT_BEGIN
Testing - Monitoring - Basic Concepts

◼ To dynamically verify a system (i.e., to find errors and debug
  them), it must be possible to observe its run-time behaviour
◼ Monitoring
   ● Gathering of run-time information through observations
   ● Basis for debugging and performance measurements
◼ Difficulties in embedded systems monitoring
   ● Insufficient interfaces to the outside world
   ● Probe effect - The actual act of observing can change the system
     behaviour -> Observation must not disturb, or intrude on, system
     behaviour
◼ Two difficulties affecting observability
   ● Race condition
   ● Probe-effect

## [L08 / PDF 013 / L8-13] Testing - Monitoring - Race Condition
@@TEXT_BEGIN
Testing - Monitoring - Race Condition

◼ Race condition with respect to the order of access to
  shared resources
  ● Race conditions are natural in multi-tasking real-time
    systems
  ● Different inputs to the racing tasks may lead to different
    execution paths
    -> Lead to different execution times for the tasks
    -> Different orders of access to the shared resources
    -> Different system behaviours if the outcome of the
    operations on the shared resources are depending on the
    ordering of accesses
@@TEXT_END

## [L08 / PDF 014 / L8-14] Testing - Monitoring - Race Condition Example
[VISUAL_ASSETS] This page contains 2 image object(s); selectable PDF text is extracted below.
@@TEXT_BEGIN
Testing - Monitoring - Race Condition Example

◼ Path 1
   ● Task B enters the critical
     section before A when A has
     its worst case execution
     time
   ● Task A is pre-empted by
     task B
   ● The resulting transaction
     yields a value of A(B(X))
◼ Path 2
   ● Due to shorter execution
     time, task A starts and
     terminates before task B is
     released
   ● The resulting execution path
     is A -> B yielding a value of
     B(A(X))
                                    (eg)   Task A: x++;
                                           Task B: x=0;
@@TEXT_END

## [L08 / PDF 015 / L8-15] Testing - Monitoring - Probe Effect
@@TEXT_BEGIN
Testing - Monitoring - Probe Effect

◼ Non-deterministic effect of intrusively observing a
  system
◼ In the previous example of race conditions:
   ● If a probe is inserted to task A so that its execution time
     needs to be extended -> Only path 1 scenario is possible
   ● If path 2 is erroneous, this will not be revealed during
     testing
   ● If the probe is removed from task A after satisfactory
     testing, the path 2 scenario may occur leading to a failure
@@TEXT_END

*Testing - Monitoring - Collecting Sufficient Information

 ◼ The amount of information needed depends on:
    ● The fault hypothesis on which the observations take place
        ❖The more fault hypothesis, the more information needed

    ● Too little information -> Insufficient for achieving the

## [L08 / PDF 017 / L8-17] *Testing - Monitoring - Passive Hardware Probes (1)
@@TEXT_BEGIN
*Testing - Monitoring - Passive Hardware Probes (1)
◼ Types of testing probes
   ● Non-intrusive/passive hardware approach
   ● Intrusive software instrumentation approach
   ● Hybrid to minimise the software instrumentation
◼ Hardware monitoring approach
   ● To reduce the perturbations caused by monitoring software
      ❖ Any software instrumentation requires memory and execution
         time resources
      ❖ But, hardware can passively monitor the system with no
         interference
   ● Example: A special monitoring hardware allows non-intrusive
     access to memory through dual-port memories or through the use
     of CPU emulators
      ❖ The monitoring hardware is interfaced through the CPU socket
         (emulator) or the system busses -> It can observe the target
         system without interfering with its execution

*Testing - Monitoring - Passive Hardware Probes (2)

◼ Drawbacks
   ● Increased cost
      ❖The monitoring mechanisms are target specific
      ❖Dedicated monitoring hardware on each node
      ❖Dedicated network for monitoring data transfer and
        synchronisation (to avoid probe-effect)
   ● Non-portability and the lack of scalability
   ● Observations are on a low level of detail

Testing - Monitoring - Software Probes (1)

Testing - Monitoring - Software Probes (2)

Testing - Monitoring - Reproducibility

◼ A system is reproducible if it is deterministic with
  respect to a behaviour P, and it is possible to
  control the entire set of necessary and sufficient

   ● To find the error when a failure has been observed

   ● To show that no new errors have been introduced when
     correcting another error

## [L08 / PDF 025 / L8-25] *Testing - Executing - Fault Injection
@@TEXT_BEGIN
*Testing - Executing - Fault Injection

◼ During normal operation, faults are rare events ->
  artificial fault injection is required to test and debug a
  fault-tolerant mechanism
   ●   It is difficult to identify the causes of failures during operation
   ●   Particularly hard to recreate a failure scenario for a large, complex
       system
◼ Fault injection:
   ●   An experiment-based approach to study the dependability of a
       system
   ●   Intentional insertion of faults into an operational system by
       hardware or software means to determine its response under fault
       conditions
   ●   Can speed up the occurrence and the propagation of faults for
       observing their effects on the system performance

*Testing - Executing - Fault Injection Methods

◼ Faults can be injected into either the physical level of
  the hardware or the state of the computation
◼ Hardware methods
   ●   Can inject faults into chip pins and internal components (e.g,

   ●   Used to evaluate low-level error detection and masking

◼ Software methods
   ●   Convenient for producing changes at the software-state level

   ●   Less expensive
   ●   A higher perturbation overhead because they execute software

## [L08 / PDF 030 / L8-30] Testing - Difficulties in Networked System (1)
@@TEXT_BEGIN
Testing - Difficulties in Networked System (1)

◼ Reproducibility in sequential programs
  ● Only the sequence of inputs & initial conditions must be controlled
  ● Given the same initial state and inputs, the sequential program
    deterministically produces the same output on repeated
    executions, even with systematic faults or intrusive probes
◼ In networked real-time, timing and order issues are
  complicated
  ● Hard to break-point on different nodes at exactly the same time ->
    cannot achieve timely reproduction of outputs
  ● Many paths of control -> halting one control path introduces a
    temporal distortion in the control flow
◼ Possible solutions to testing of networked systems
  ● To send stop/start messages from one node to other nodes with
    message latency
  ● A priori agreed times when the executions should be halted or
    resumed
@@TEXT_END

@@TEXT_BEGIN
Testing - Difficulties in Networked System (2)

◼ Testing of networked systems is relatively new
  subject
◼ Major issues in testing of networked systems
   ● How to extract sufficient information from the system?
   ● How to eliminate the perturbation that the observations
     cause? (probe effect)
   ● How to reproduce the observations?
      ❖How to alter the control flow by manually or conditional
        breakpoints to increase the observability
   ● How to correlate the observations - how to define a global
     state?

Testing - Executing (NCS) - Execution Order Analysis

◼ A typical executing method for networked systems
◼ To transform the problem of non-deterministic

## [L08 / PDF 033 / L8-33] Testing - Executing (NCS) - Execution Order Analysis (Jitter)
@@TEXT_BEGIN
Testing - Executing (NCS) - Execution Order Analysis (Jitter)

 ◼ Jitter increases the number of execution order scenarios ->
   should be reduced to increase testability
 ◼ Typical types of jitter affecting the testability
    ● Execution time jitter
        ❖ The difference between execution times WCET (Worst case) and
          BCET (Best case) of a task
    ● Start jitter
        ❖ The inherited and accumulated jitter due to execution time jitter
          of preceding higher priority tasks
    ● Clock synchronisation jitter
        ❖ Clock corrections cause varying inter-arrival times between
          clock ticks
    ● Communication latency jitter
    ● Interrupt induced jitter
        ❖ Execution time variations induced by the pre-emption of
          interrupts
@@TEXT_END

## [L09 / PDF 004 / L9-4] Software Defect Reduction [Boehm, 2001]
@@TEXT_BEGIN
Software Defect Reduction [Boehm, 2001]

1. Fix problems early - fixing a problem after deliver is 100 times
    more expensive
2. Avoidable rework is upto 40-50% of current costs
3. 80% of avoidable rework comes from 20% of the defects
4. 80% of defects come from 20% of modules
5. 90% of the downtime comes from 10% of the defects
6. Peer review catches 60% of defects
7. Perspective-based reviews are 35% more effective than non-
    directed reviews -> assign roles to reviewers for specific areas
8. Disciplined design practices reduce defects by upto 75%
9. Dependable code costs 50% more per line to write, but less
    cost for life-cycle
10. 40-50% of user programs contain non-trivial defects
@@TEXT_END

## [L09 / PDF 009 / L9-9] 22 - Large if-then-else or case Statement
@@TEXT_BEGIN
22 - Large if-then-else or case Statement

◼ Problems
  ● So many different paths -> Extremely difficult to debug
  ● The difference between best-case and worst-case execution
    time is significant
      ❖Under-utilizing the CPU
      ❖Possibility of timing errors
  ● Testing cases grow exponentially with the number of
    branches
◼ Alternatives
  ● Lookup tables, finite state machine, boolean algebra, etc
  ● (eg) if(x==1) x=0; else x=1; -> x=!x;
@@TEXT_END

@@TEXT_BEGIN
19 - No Software Engineers in Hardware Design

◼ For new products (no hardware defined), software

  ● To select a system architecture minimizing the overall cost

  ● Avoiding laziness in thinking about the design

18 - No Emulators of Target Application

◼ Compiling, downloading, then executing code on a

  ● Each module should be tested individually for its

  ● Easy to get customer feedback even before the hardware is

## [L09 / PDF 015 / L9-15] 16 - Generalization based on Single Architecture
@@TEXT_BEGIN
16 - Generalization based on Single Architecture

◼ To develop software to run on various processors,
  programmers write software for one of the
  platforms, and generalize everything for porting the
  code at a later time
   ● Over-generalizing items that are very similar on different
     architectures
   ● Not generalizing some items that are different
◼ A better strategy
   ● Choose three or four processors that are very different
   ● Design and develop the code simultaneously on multiple
     architectures
   ● Generalize only those parts that are different in the different
     architectures
@@TEXT_END

## [L09 / PDF 016 / L9-16] 15 - Optimizing at the Wrong Time
@@TEXT_BEGIN
15 - Optimizing at the Wrong Time

◼ For a real-time system, aware of the timing
  implications of every single line of code
◼ Coarse-grain optimization
   ● Involves major design decisions to be considered before
     implementations
◼ Time taken to add two numbers (6MHz Z180)
   ● Two 16-bit = 7us, two 32-bit = 12us, two floats = 28us
   ● An 8-bit and a float = 308us (due to long conversion time)
◼ For the Z180, doing everything in float is better than
  having mixed-type arithmetic
◼ With a floating-point accelerator
   ● Ten times faster than a 33MHz 68882
   ● Same for sin() and cos() because the 68882 has built-in
     trigonometric functions
@@TEXT_END
@@PAGE_END lecture=L09 pdf_page=016

@@PAGE_BEGIN lecture=L09 pdf_page=017 slide_label="L9-17" slide_title="15 - Optimizing at the Wrong Time (cont’d)" image_xobjects=0
## [L09 / PDF 017 / L9-17] 15 - Optimizing at the Wrong Time (cont’d)
@@TEXT_BEGIN
15 - Optimizing at the Wrong Time (cont’d)

◼ Fine-grain optimization (eg, x+x+x for 3*x)
  ● Poor readability, or may slow down code
  ● Fine-grain optimization from the beginning may lead to an
    unreadable code
◼ Rule of thumb
  ● Do not perform fine-grain optimization during
    implementation
  ● If necessary, do fine-grain optimization during the
    debugging phase
  ● If unnecessary then keep the more readable code
@@TEXT_END

14 - Reusing Code Not Designed for Reuse

◼ To reuse the code having interdependencies
   ● If all of it taken, more code than needed

## [L09 / PDF 019 / L9-19] 13 - Blocking Forms of Message Passing
@@TEXT_BEGIN
13 - Blocking Forms of Message Passing

◼ Message passing - Functional blocks with inputs &
  outputs implemented as messages
  ● Problematic IPC(Inter-Process Communication) for real-time
    systems
◼ Problems
  ● It requires synchronization - a source of unpredictability to
    real-time scheduling
  ● Deadlock is possible in bi-directional communication
    between processes
  ● More overhead as compared to shared memory
◼ To simply use shared memory & semaphores is not
  good - as semaphores have the same problems
◼ Many IPC methods are available to improve the
  robustness & reliability of the real-time system
@@TEXT_END
@@PAGE_END lecture=L09 pdf_page=019

@@PAGE_BEGIN lecture=L09 pdf_page=020 slide_label="L9-20" slide_title="13 - Blocking Forms of Message Passing (cont’d)" image_xobjects=0
## [L09 / PDF 020 / L9-20] 13 - Blocking Forms of Message Passing (cont’d)
@@TEXT_BEGIN
13 - Blocking Forms of Message Passing (cont’d)

◼ State-based communication by creating local copies
  of shared data
   ● The latest data is always available to process when needed
   ● Robustness against lost messages, unsynchronized code
     execution rate
   ● Less OS overhead if shared memory is used
◼ (Ex) Train braking system
   ● Message-based: “apply brake” messages result in
     dependencies -> difficult to analyze & deadlocks
   ● State-based:
      ❖Each brake module executes periodically and monitors
        the variable to update the state of its own brake I/O
      ❖Processes are periodic -> easy analysis of schedulability
      ❖Use a single state table -> no direct dependencies
@@TEXT_END

## [L09 / PDF 022 / L9-22] 11 - Improper Use of Global Variables
@@TEXT_BEGIN
11 - Improper Use of Global Variables

◼ Global variables are used for
  ● Interrupt handlers
  ● Shared memory
◼ However, global variables
  ● Violate encapsulation criteria of object-based design
  ● Make it more difficult to maintain the software
  ● Prevents reuse of software modules
◼ Automatically shared among all processes ->
  conflicts
  ● Any access to shared memory must be guarded as a critical
    section to prevent race conditions (eg, semaphores)
  ● But, they are not real-time friendly, and can create priority
    inversion
@@TEXT_END

@@PAGE_BEGIN lecture=L09 pdf_page=023 slide_label="L9-23" slide_title="10 - Indiscriminate Use of Interrupts" image_xobjects=0
## [L09 / PDF 023 / L9-23] 10 - Indiscriminate Use of Interrupts
@@TEXT_BEGIN
10 - Indiscriminate Use of Interrupts

◼ Interrupts are the biggest cause of priority inversion
   ● Interrupts preempt everything else and are not scheduled
   ● Preempting a regularly scheduled event causes undesirable
     behavior
   ● An ideal real-time system has no interrupts
◼ Interrupts have less OS overhead than a context
  switch, but handlers
   ● Always have high priority and can cause priority inversion
   ● Reduce the schedulable bound of the real-time scheduling
     algorithm -> counteracting any savings in overhead
   ● Execute within a different context and force the use of
     shared global variables
   ● Are difficult to debug and analyze because few debuggers
     allow the setting of breakpoints or performing user I/O
     within the handler
@@TEXT_END
@@PAGE_END lecture=L09 pdf_page=023

## [L09 / PDF 024 / L9-24] 10 - Indiscriminate Use of Interrupts (cont’d)
@@TEXT_BEGIN
10 - Indiscriminate Use of Interrupts (cont’d)

◼ Minimize the use of interrupts when possible
  ● Their only function is to signal an aperiodic server
◼ Never assume that overhead from interrupts is
  negligible
@@TEXT_END

## [L09 / PDF 026 / L9-26] 8 - It’s Just a Glitch
@@TEXT_BEGIN
8 - It’s Just a Glitch

◼ Any “glitch” means something is wrong! -> need to
  understand the problem
◼ Most common problems associated with glitches
   ● Race condition
   ● Memory corruption
   ● Deadlock or priority inversion
◼ For new applications
   ● Take precautions during the design and implementation
   ● Code review
◼ For addressing race conditions
   ● Minimize the number of global variables or shared memory
     segments
   ● Minimize preemption and the number of interrupt handlers
@@TEXT_END
@@PAGE_END lecture=L09 pdf_page=026

@@PAGE_BEGIN lecture=L09 pdf_page=027 slide_label="L9-27" slide_title="8 - It’s Just a Glitch (cont’d)" image_xobjects=0
## [L09 / PDF 027 / L9-27] 8 - It’s Just a Glitch (cont’d)
@@TEXT_BEGIN
8 - It’s Just a Glitch (cont’d)

◼ For memory corruptions
   ● Use a tool (eg, Purify) to identify all possible problems
◼ For avoiding deadlocks
   ● Use the priority ceiling protocol
◼ For priority inversion
   ● Do not use interrupts
   ● Use proper real-time scheduling methods
◼ To track down a race condition
   ● Put a “sleep()” command before and after every access to a share
     data item -> slow down the code and the race condition occur
◼ To track down a memory problem (stack overrun)
   ● Initialize all of the memory allocated for the stack with a non-zero
     and non-0xff (eg., 0x55)
   ● If the glitch occurs, check if there are still 0x55 in the memory
   ● If not, then a stack overrun did occur
@@TEXT_END
